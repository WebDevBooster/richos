# User application updates

This crate stages verified RichOS updates under the current user's `~/Applications` and activates them on the next ordinary launch. It never invokes an installer, shell, administrator authorization or the plugin's privileged installation fallback. The caller supplies only bytes returned by signature-verifying `tauri_plugin_updater::Update::download`.

`stage_verified(home, bytes, version)` checks archive containment, bundle identity and the complete extracted tree. Before recording readiness it runs the signed executable's startup-only identity probe inside a sandbox that denies writes, networking, process creation and GUI access. Inherited descriptors are marked close-on-exec, output is bounded and the probe has a timeout. Its compiled version must match the offered release. A separate staging lock and shared session lease keep extraction and probing off the short publication lock, so another ordinary startup can open the current app during a download. Staging changes neither the running application nor a protected system installation. The live updater never exits or restarts the application.

At normal startup, before threads or input, acquire `StartupLease`. An exclusive lease permits `activate_prepared(lease, compiled_version)` to publish the next version using an atomic directory exchange. A shared lease permits running and exact redirection but forbids activation. `with_preferred` validates the publication receipt and complete tree while holding publication exclusion through the callback's `StartupLease::exec`. The internal inherited descriptor hint is validated against the exact owner-private session lock; the redirected child adopts it as shared. Keep the shared lease until process exit. The shipping bootstrap also verifies its own loaded bundle identity and prevents redirect loops or downgrades.

## Going back to an earlier release

`rollback_target(home)` answers where back is, from this installation's own history: `recover` writes `previous.json` into the transaction directory before it exchanges the bundles, and `collect_retired` reclaims that transaction's payload while leaving its receipts — so the version is answerable long after the old application is gone. Only that note's `version` is used. Its `archive_sha256` is the digest of the archive that REPLACED it and its `tree_sha256` describes a directory that no longer exists; both would be wrong answers to "which release do I fetch". Three answers: the version, no record at all, or a record that points forwards because the last activation was itself a rollback.

`stage_rollback_verified(home, bytes, version)` takes the same bytes contract as `stage_verified` — only what signature-verifying `Update::download` returned — and goes through the same extraction, identity probe and publication receipt. It refuses unless `version` is exactly the one `rollback_target` named, so the only reachable destination is the version this installation was demonstrably running an update ago; it refuses a pending prepared update rather than superseding it; and it writes `rollback.json`, naming the prepared archive AND the version it was staged to leave.

That file is the only thing that may move this installation backwards, and activation accepts a downgrade only when both facts still hold at the moment of exchange, under the publication lock. A receipt overtaken by an update in between authorizes nothing and is retired exactly as an obsolete forward update is. It is written before the journal it authorizes and cleared before one it does not, so the only reachable crash state is "authorizes nothing", and it is consumed on use.

`activate_prepared` and `recover` return `Activation { entered, left, rollback }`, also written to `last-activation.json`: an update and a rollback are the same exchange of two directories, and only the receipt that authorized it tells them apart — at the moment it is consumed. `last_activation(home)` reads it back, for the boot line and for a second launch that has to reach the same verdict about an older publication as the one that performed the exchange.

The prepared journal survives interruption. Replay of an already exchanged app persists both rename directories and finishes its receipt without exchanging again, including when the running version already equals the update. A newer valid offer can supersede an obsolete pending update. Starting a newer external build retires an exact obsolete prepared receipt; shared sessions also ignore obsolete readiness when checking the server. Invalid prepublication receipts are quarantined only when an independent receipt proves the old application is intact; ambiguous post-exchange damage remains retained. A failed identity probe or newer destination never causes an older payload to be published.

`collect_retired(lease, loaded_bundle)` reclaims up to eight proven updater payloads at an exclusive startup before activation. The caller first verifies its loaded bundle has not changed. Collection skips the loaded bundle inode and current prepared transaction. Previous applications, superseded payloads and incomplete extractions require their own exact tree receipt or original allocation identity. Durable identities use the native volume UUID and inode, so a changed device number after reboot does not invalidate them. A durable retirement journal binds both directory identities before deletion, allowing replay after partial removal. Small audit receipts remain. Unknown or changed payloads are retained; collector errors are logged without blocking normal app use. Unreceipted leftovers from older implementations are not silently adopted.

The user-owned journal provides crash recovery, not isolation from arbitrary code with the user's filesystem rights. Worker confinement must deny writes to the application and updater namespace. Participating application sessions honor the lifetime lease; arbitrary older binaries that predate this protocol do not. POSIX ownership, safe ancestors, macOS ACL write grants, symlink containment and external hard links are checked independently.

Run the owner-only macOS tests:

```sh
cargo test --manifest-path richos/app/crates/richos-user-update/Cargo.toml --offline
```

Tests use tiny native fixture binaries and import the shipping startup module for a real exec-transfer test. They exercise containment, permissions, atomic exchange, crash replay, compiled identity refusal, lease exclusion and receipt-bound cleanup without opening a GUI or installing a release. They do not claim to test upstream signature verification. The separate signed updater E2E harness isolates `HOME`, stages during one fixture session and verifies activation on the next launch.
