# The CEO TODOs — the starter kit an adopter actually receives

The engine ships a lint (`scripts/ceo-todos-lint.sh`), a commit guard
(`scripts/hooks/guard-ceo-todos-commits.sh`), a predicate
(`scripts/lib/ceo-todos.{sh,py}`) and a test suite for all of it.

**Every one of them is inert until a repository carries a `.ceo-todos`
declaration.** For one release they shipped without one, without a template,
and without a mention in the onboarding runbook — so an adopter received
enforcement machinery that could never fire, and nothing told them. That is the
same defect the machinery itself exists to catch (present, correct, and
unreachable), one level out, and it is why this folder exists.

## Do not copy these by hand

```bash
scripts/ceo-todos-init.sh /path/to/your/repo
```

It writes the declaration, a starter record, the transcript folder, renders the
first `CEO-TODOs.md`, puts a pointer at the top of your `README.md`, and then
runs the lint so you see the mechanism work on your own repository before you
have typed anything into it.

An empty TODO list is not an empty page: it renders as **"Nothing is waiting on
you"** with both sections shown, so the surface exists and its shape is obvious
from the first minute rather than appearing the day something lands on it.

## The files here

| file | what it becomes |
|---|---|
| `ceo-todos.example` | the repository's `.ceo-todos` declaration |
| `open-items.md` | the starter record, with one worked example in section 3 |
| `cold-open-README.md` | the note dropped into the transcript folder |

They are templates with `@@PLACEHOLDER@@` markers, not drop-in files. Read them
to understand the format; run `ceo-todos-init.sh` to install them.

## The one thing to understand before you start

The record is the source. `CEO-TODOs.md` is a projection of it, regenerated by
`scripts/ceo-todos-render.sh`, and the commit guard refuses a projection that
is not byte-identical to what the record renders to. **Never edit the TODOs
page.** Edit the record; re-render.

## The premise of a question

An item can be perfectly prepared, not yet finished, and still not worth his
time — because the fact its question rested on has stopped being true. That is a
third failure, distinct from "unprepared" and from "already done", and it is
checked by the sibling contract rather than by this one: see
[`../row-currency/README.md`](../row-currency/README.md), "The second warrant".

Two optional keys in this declaration switch it on, and one optional item field
carries it:

```
PREMISE_SECTIONS="1 2"     # a subset of CEO_SECTIONS. Undeclared = not adopted.
PREMISE_REQUIRED="0"       # 1 makes a premise-less item a refusal, not a notice.
```

```
- **Premise:** `<repo>/src/scope.rs`@`4f2a9c1e83bd` — the fact this question rests on
- **Premise:** `unobservable "he types a command; nothing on disk records that he did"`
```

The pin is never rendered onto the CEO's page. It is machinery, and his
attention is the thing all of this exists to protect.
