UI-SUITE-CI — THE RUNS THAT PROVE THE GATE CAN REFUSE
=====================================================

`.github/workflows/ui-suite-ci.yml` reports on twelve browser suites. The whole reason it
was written is that a green CI run which did not actually execute the suites is worse than
no CI at all: it converts "nobody checked" into "somebody checked and it was fine". This
repository has produced exactly that twice in one week — a scanner reporting CLEAN over an
empty corpus, and a `run.js` reporting "all 4 suites passed" over a suite it was not
running. Both exited 0, honestly.

So the workflow's claim is not "the suites passed". It is "twelve suites ran and reported
this many checks, and here are the numbers". That claim is only worth something if the
machinery behind it can say no. Below is every new check, run RED once, by breaking the
SHIPPED source and watching it refuse.

WHERE THESE RAN. A copy of the tree extracted with `git archive` from the git tree object —
tracked files only, no `node_modules`, no `.env`, nothing untracked — with
`RICHOS_PLAYWRIGHT` removed from the environment with `env -u` and the browser cache
pointed at a directory created empty for the purpose. One edit per run; the tests directory
was restored from the tree object after each, whether it passed or failed.

READ M1 FIRST. It is the one the CEO's sentence is about: every process exits 0, every
suite's own checks pass, and the run is refused anyway.

  eleven times at once. It is a backstop for a case the per-suite rules already catch,
  and it has never been the only thing between a run and a green badge.
