## Item 5 — the way back

**Absent, and absent correctly.** Settings → Updates, with the window grown to 1010 px so the whole
panel is on screen (`11-settings-updates-full-panel.png`), ends at:

> **Updates** · RichOS 1.2.0-nightly.20260920.2 is up to date. · Checked 2 hours ago. ·
> [Check for updates] · Update server: `https://github.com/WebDevBooster/richos/releases/download/nightly/latest.json` · Bust a bug!

No *"Go back to …"* row, before or after pressing **Check for updates**.

The reason is structural, and I checked it on the guest rather than inferring it from the screen:

```
$ find /Users/admin/testvm/ray10/home -name published.json -o -name previous.json
                                                     (nothing)
```

`resolve_rollback` (`richos-user-update/src/lib.rs:1771`) returns `NoRecord` without `published.json`,
and `refresh_rollback_target` maps `NoRecord` to `None`, so the UI omits the control — which is
exactly what `updates.rs:658` says it must do (*"a stale 'Go back to 1.2.0' on a copy that is already
on 1.2.0 is worse than no control at all"*). **`run.sh` installs the bundle by copying it in, never
through the updater**, so a guest has no publication history and there is nothing for the control to
point at.

**So this is a harness gap, not a product verdict.** To walk the way back, a guest has to install
`.1` *through the updater* and then update to `.2`; nothing in `testvm/` does that today. Item 5 is
NOT REACHED and nothing about `8dbd926c` is confirmed or denied here.

## Defects found, ranked

### 1. HIGH (product) — §55 is missed on 4 of 5 turns, and the app says why

First words at 8.5 / 10.7 / 13.0 / 14.1 / 14.5 s against a 9 s budget, uncorrelated with host load.
The app's own log charges 24 spine waits to §55, the largest **14,340 ms**, at
`src-tauri/src/main.rs:4158`. This is the whole of the gap; nothing else needs to be searched for.

### 2. HIGH (product) — a thread switch shows an empty pane under the wrong title for ~5 s

5,102.4 ms blank, of which 4,967.9 ms with the breadcrumb still naming the conversation just left.
Frames `07-…png` and `08-…png`. The chip itself is correct and well-worded; the pane and the
breadcrumb are not.

### 3. MEDIUM (product) — phone → Mac is ~3x slower to the ledger and ~7x slower to the screen than `.1`

2.06 s to `intake.jsonl`, 5.07 s to the bubble, against `.1`'s 0.69 s and ≤0.71 s. One sample, on a
loaded host, so **confirm before acting** — but the direction is wrong and this is the leg CEO §61
deleted the LAN fallback for.

### 4. MEDIUM (harness, blocks item 6 and cost this walk ~25 minutes) — the fixture keychain re-locks, and the app's prompt is invisible

`keychain.sh prepare` reports `gui-session=usable`, but asked in the app's own session seven minutes
later the keychain says:

```
Keychain ".../login.keychain-db" lock-on-sleep timeout=300s
```

— i.e. the `set-keychain-settings` the script's own header says removes the timeout (*"NO TIMEOUT AND
NO LOCK ON SLEEP"*) **did not take**. It is issued only in the ssh session, with its output and its
exit status discarded. Applying it through `launchctl asuser` by hand turned the same keychain into
`no-timeout` in one call.

The consequence is not cosmetic. `Set my phone up` raised
`security wants to use the "login" keychain` **behind the sheet**, and the app gave up:

```
[richos] the phone channel could not start: security: still running after 120s, killed
```

The modal came back **at least six more times** during the walk, each time blocking accessibility
reads for up to 300 s. Ray raised this on `.7`, on `.8` (defect 4) and again as `.1` H2; it is still
here. `ax.sh --windows` still does not list it, so a tester who does not know to look sees a hang.
**Fix: issue `set-keychain-settings` in the GUI session and check its result**, the same way the
unlock already is.

### 5. MEDIUM (harness) — `ax.sh click --at` has never worked, and it is the fallback for exactly the controls that need it

```
$ ax.sh ray10 click --at 637,686
[testvm] ax: clickfailed — Error: Can't convert types.
```

The frontmost check passes and `se.click({ at: [x, y] })` throws in JXA (`ax.js:206`). The
coordinates are parsed as numbers (`ax.sh:169`), so this is the JXA call itself. The AppleScript
form works and is what this walk used:

```
$ osascript -e 'tell application "System Events" to click at {637, 686}'
text area Message to Rich of group 2 of UI element 1 of … of application process richos-tauri
```

### 6. MEDIUM (harness) — a click does not focus a web-view text field, and nothing in the toolkit focuses one

The click above lands **on** the composer and reports it, but `ax.sh --focused` still shows the web
area and keystrokes go nowhere — silently. Three attempts typed into a void before this was noticed.
What works is setting the attribute:

```
osascript -e 'tell application "System Events" to tell process "richos-tauri" to set focused of
              text area "Message to Rich" of … to true'
```

Both composers in this walk (the Mac's and the phone page's) needed it. **`ax.sh` should grow a
`focus --title <text>`**, so the next walk does not rediscover this; I did not add it because it
belongs in `testvm/ax.sh` beside `click`, and `ax.js` needs the path-walk that `find` already has.

### 7. LOW (harness) — `run.sh` cannot exercise the updater, so items like 5 cannot be walked

See item 5. A guest that gets its app by `cp` has no publication history.

### 8. LOW (product, naming) — `RichOSSourceCommit` holds the build commit

`Info.plist` says `RichOSSourceCommit = 94261241…`; the source commit is `50c863c3…`. Whoever reads
that key for a freshness check reads the wrong one. The value is right for a build identity; the
name is wrong for it.
