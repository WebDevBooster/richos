THE FEEDBACK CHANNEL — THE TWENTY-FIVE RUNS THAT PROVE THE SUITE CAN FAIL
=========================================================================

`app/ui/tests/feedback.js` reports 24/24 and 111 assertions against the tree as it stands.
That number is worth nothing on its own: a check that has never failed has proven nothing,
and this repository has produced both kinds of green in one week — a scanner reporting
CLEAN over an empty corpus, and a `run.js` reporting "all 4 suites passed" over a suite it
was not running.

So every check in the suite was run RED, once, by breaking the thing it guards in the
SHIPPED source (`app/ui/index.html`, `app/ui/main.js`, `app/ui/style.css`,
`app/ui/mock.js`, `app/src-tauri/src/main.rs`) and watching the suite say so.

The driver applied exactly one edit per run, REFUSED to proceed unless the target string
matched exactly once, restored the file from a copy taken before the edit whether the run
passed or failed, and `git status` was clean of stray files at the end. The mutations are
also listed inside `feedback.js` itself, against their check numbers, so the two cannot
drift silently.

The mutation TAGS below are the driver's and were fixed before the suite's checks were
renumbered (there was no check 5; 6 became 5, 10 became 8, and so on). The FAIL lines are
the suite's own output at the numbering that shipped, so each block names both.


THREE OF THESE DESERVE A NOTE
-----------------------------

  * MUTATION 6b WAS A BAD MUTATION ON ITS FIRST RUN, AND THE CHECK WAS STRENGTHENED RATHER
    THAN THE MUTATION ABANDONED. Removing the sort from `mock.js`'s `feedbackAssemble` left
    check 5b GREEN. The reason is worth writing down: `chosen()` reads
    `querySelectorAll('input[name=…]:checked')`, which returns DOM order, so the surface
    hands the assembler vocabulary order no matter what order the CEO clicked in — ticking
    the boxes in reverse can never detect an unsorted assemble. The check now does that AND
    posts the reversed selection through the bridge, which is the only path that reaches
    the assembler; the same mutation then turns it red. What the DOM half proves is still
    worth keeping and is now stated as what it is: the surface cannot reorder a selection.

  * MUTATION 4 (dropping the contributing-condition group) turns FIVE checks red, and that
    is the right answer rather than noise. The reference selection includes two conditions,
    so with the group gone it cannot be made at all and everything downstream of it — the
    preview, the reverse-order case, the approval and the refusal — fails with it. A
    mutation that only ever turns one check red is not automatically a better mutation; one
    that turns EVERY check red is (see the note in the correction desk's own record, where
    an unbalanced `if` stopped `main.js` parsing and proved nothing about anything).

  * MUTATION 14 (dropping `closeFeedback()` from the Escape chain) turns check 3c red as
    well as check 12, because 3c presses Escape to prove that CLOSING the panel records
    nothing. That is a real dependency and it is listed rather than engineered away: 3c's
    claim is about the dismissal, and it needs a working close to make it.
