## A correction to my own method, stated before any finding rests on it

**Two of my working assumptions were wrong today, and both would have produced false findings.**

**1. `cliclick kp:esc` and `cliclick kp:return` are not reliably received by this app's WebKit
view.** My first Escape presses appeared to do nothing on three different sheets. They also
appeared to do nothing when I pressed Return to send. The positive control that settled it:
`osascript -e 'tell application "System Events" to key code 36'` sent the same composer contents
**immediately** (`25-return-via-sysevents.png`), and `key code 53` closed the settings sheet
(`30-escape-settings-sysevents.png`). Typing text with `cliclick t:` works fine; the special keys
are the problem. **Every keyboard claim in this file after 19:03 uses System Events**, and I
re-ran the Escape and Return rows on that path.

**This has a consequence for the record.** The .9 audit's row *"Escape does not close the settings
sheet — FAIL (carried)"* was produced with `cliclick` and a positive control that only proved
**text** injection worked. On this build, with a control on the **same key**, Escape closes the
settings sheet, the company picker and the techy-mode sheet. That row should be re-derived on
.9 rather than carried forward.

**2. The image renderer I read screenshots through is not faithful to the original hues.** Reading
`42-dark-mode-settled.png` I saw a cream conversation pane inside a dark-chrome window and was
about to file "dark mode is only half applied" as an obvious visual defect. The pixels say the
pane is `#0c1322` — 307,580 of them — with `#dfe4ee` text. **Dark mode is applied correctly and
there is no defect.** Measured, not eyeballed, exactly as the standing rule says.

## 5. Closing the window — the red button quit the app

**This is a finding, and it also ended the first half of the walk.**

At 19:12:24, with **no work running**, I clicked the window's red close button, expecting .9's
documented result: process stays, Dock icon brings it back. Three seconds later:

```
$ osascript -e 'tell application "System Events" to tell process "RichOS" to count windows'
61:74: execution error: System Events got an error: Can't get process "RichOS". (-1728)
$ pgrep -fl 'richos-tauri'       → (empty)
$ ps -p 32095                    → GONE
```

**The app quit.** `app.log` carries no line about it — where .9 wrote *"[richos] window closed
with work registered: RichOS stays running with no window. The Dock icon brings it back."*, this
launch wrote nothing at all.

**What this means for a person:** the same red button does two different things depending on
state he cannot see. With work registered it hides the window and keeps the app alive; with
nothing registered it ends the app. Neither is announced. A Mac user's model of the red button is
"close the window", and on this path it is "quit". There is no dialog either way.

I am **not** calling this wrong. Quitting on last-window-close when there is nothing to protect is
a defensible choice, and the protective case — the one that matters — is the one .9 proved works.
I am recording that the behavior is **bimodal, silent, and undocumented on screen**.

**Row 5 / §7.4 is therefore answered only in the negative case.** A positive control needs a job
that survives longer than 40 s, which this build does not produce. What it would need: the
settlement defect fixed, then close → `pgrep` → Dock restore → thread and job intact → quit
through the menu and read the dialog.
