## 1. The blocker, with the exact refusals

**Basis: ran it.** Three attempts, each a different shape, each refused before execution:

| Attempt | Refusal |
|---|---|
| `env -i HOME=<scratch> … security find-generic-password …` | *"this command sets HOME, injecting git configuration whose effect on where git writes can't be verified"* |
| The same behind `cd /tmp && …` — **the exact form the `.1` walk used successfully this morning** | Identical refusal |
| `env -i GIT_CONFIG_GLOBAL=/dev/null GIT_CONFIG_SYSTEM=/dev/null HOME=<scratch> …`, pinning the very thing the guard says it cannot verify | *"this command sets GIT_CONFIG_GLOBAL, injecting git configuration…"* |

It is the **harness** control, not an engine hook: `settings.local.json` registers exactly one
`PreToolUse` hook and its matcher is `Agent`, not `Bash`. It offers no marker escape hatch — unlike
`main-checkout-run:` or `resume-ack:`, there is nothing to declare.

**What I did not do, deliberately.** The assignment could be hidden inside a script file, which is
how a shell command carrying it becomes invisible to the guard. That is evading a blocking control
in my own session, so I did not do it — and I am naming the option here rather than leaving it for
someone to discover and take quietly.

**Why a scratch home is not merely the brief's preference.** The app has no root data-directory
override. `RICHOS_ENGINE_DIR`, `RICHOS_PROJECTS_DIR`, `RICHOS_SESSIONS_DIR` and the rest redirect
pieces, but the Tauri application-support directory under `~/Library/Application Support/` and the
`$HOME/myrichos` literal (`crates/richos-core/src/company.rs:103`, no override) are home-derived.
Isolation without a home redirect is therefore not available at any price.

**What would unblock it, cheapest first:**

1. Re-dispatch this walk from an agent **not** natively worktree-isolated (the cross-repo workspace
   alone is enough for the commits), or have the main session run the launcher.
2. Failing that, an explicit CEO/lead authorization to run it under a script-file launcher, recorded
   where a reviewer sees it — so the evasion is a decision, not a habit.

## 2. The brief's login premise — the mechanism is wrong, not just the outcome

The brief said, marked `unverified:`, that setting `CLAUDE_CONFIG_DIR=/Users/alex/.claude` for the
app process may be what makes a turn complete, and that check 0 is where I would find out. I could
not run check 0 — but the premise can be settled at the root without a launch, and it does not hold.

**Basis: read from source at `86d291f0`, plus the credential store on this Mac, plus the `.1` walk's
own record.**

- **That variable is the engine pointer.** `src-tauri/src/engine.rs:95` and
  `crates/richos-core/src/setup.rs:146` read it to locate `…/richos-engine`; `engine.rs:37` names it
  candidate 6 of the engine search. It is never consulted for authentication.
- **Authentication is the `claude` CLI's own login.** `crates/richos-core/src/native.rs:26`:
  *"Auth = the customer's own `claude` login. No `ANTHROPIC_API_KEY`."*
- **On this Mac that login is a keychain item, not a file.** `security find-generic-password -s
  "Claude Code-credentials"` resolves to `/Users/alex/Library/Keychains/login.keychain-db`. The
  alternative file source does not exist: there is no `/Users/alex/.claude/.credentials.json`.
  (No credential value is reproduced in this document.)
- **The CLI accepts three sources**, by inspection of the 2.1.274 binary: `CLAUDE_CODE_OAUTH_TOKEN`,
  a `.credentials.json`, and `security find-generic-password`. Under a scratch home, the first two
  are absent by construction, leaving the keychain.
- **The `.1` walk already ran with that variable set** and still spent 0 of 5 turns, its ledger
  recording `Not logged in · Please run /login`
  (`2026-09-17-nightly-1.2.0-20260917.1-onscreen-audit.md:116-126`, `:330`). So the configuration
  the brief proposes as the fix was the configuration that failed.

**The spec inherits the same assumption.** `richos-hq
docs/plans/two-installs-and-import-spec-2026-09-17.md:119-128` says the launcher points the variable
at his real one *"so the nightly uses his account"*, and `:155-158` prices the rejected alternative
as *"a fresh sign-in … for every new config directory"*. Both sentences treat the config directory
as where the login lives. The engine half of that claim is proven by the walk's boot log; **the
account half is not, and the evidence points the other way.** This matters beyond QA: the launcher
in point 6 of that spec is specified around it, so a nightly he double-clicks may open and then
refuse every turn.

**The one probe that settles it** — and the reason I want it run first, before any walk spends a
boot on it: under the scratch home, `security find-generic-password -s "Claude Code-credentials"`.
Found → the keychain is not the cause and something else refuses, and the refusal should be captured
verbatim. Not found → the keychain search list is home-relative and that is the whole cause, with
two candidate fixes (a symlink from the scratch home's `Library/Keychains` to the real one, or
`CLAUDE_CODE_OAUTH_TOKEN` supplied to the app process **from a file, never on a command line**,
where the process table would expose it). Which of those is acceptable is a decision, not a QA call.

**Stated plainly: that this is home-relative is my hypothesis, not a verified fact.** I was refused
the one command that would have settled it, and it is the first command the next walk should run.
