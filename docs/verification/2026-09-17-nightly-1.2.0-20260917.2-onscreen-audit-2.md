## Verdict

**NOT READY — one blocker, and it is check 0.**

**No turn completes.** Not one. The app is otherwise in good shape — the first-run setup, the
deferral paths, the failure cards, the voice offer and the quit/relaunch cycle all behaved well, and
every piece of text I measured passes WCAG AA in both themes. But a person who installs this and
types a sentence gets no answer, and that is the whole product.

The cause moved once during the walk, and both halves matter:

1. **Under the QA scratch home, the provider could not start at all** — `Provider could not start:
   [Errno 2] No such file or directory`. Root-caused to source. This is an artifact of the isolated
   launch **and** a real latent defect that will hit a class of real users. Raised as
   `esc-20260917T124730Z-1967c1aa`.
2. **With that worked around, the `claude` CLI itself answers `Not logged in · Please run /login`.**
   So **the keychain symlink does NOT sign the CLI in** — that is the answer to the question the
   brief asked me to settle, and it confirms the previous walk's hypothesis rather than refuting it.

**Ready for him: no.** Connecting the account is his own browser action and is not mine to take.

**Model turns attempted: 2. Turns that reached an answer: 0.** (My brief set the ceiling at six; that
ceiling is the brief's, not something this walk's evidence speaks to.) What the ledger
establishes is that both turns were interrupted before the provider produced any output — the first
because the provider process never started (`[Errno 2]`), the second because the CLI answered
`Not logged in` at the handshake. Neither ledger entry records a token count or an upstream request,
and I did not inspect his billing, so I am reporting what the app recorded rather than asserting what
his subscription was charged.

## 1. Check 0 — a turn does not complete

**Basis: ran it on screen, twice, in two different configurations.**

### 1a. First configuration — the provider never starts

Typed *"Reply with exactly: hello from the nightly."* and pressed Enter once. The app showed a
correct in-flight state (`Working for 1s`, "Rich is working / Nothing has come back yet", a stop
control), then failed. From the app's own ledger:

```
{"event":"TurnInterrupted","reason":"cognition io: claude failed to start (the child exited before
 answering the handshake); the child said: Provider could not start: [Errno 2] No such file or directory"}
{"event":"TurnInterruptionCause","record":{"cause":"transient","ceoMessage":"I lost my connection to
 the part of me that thinks, partway through. That kind of thing usually clears on its own, so asking
 again is worth a try.","offersRetry":true}}
{"event":"ActionRecorded","kind":"crash_recovery","detail":"replay interrupted turn ..."}
{"event":"TurnInterrupted","reason":"... Provider could not start: [Errno 2] ..."}   <- the auto-retry
{"event":"ActionUpdated","status":"failed"}
```

Screenshot: `2026-09-17-nightly-2-onscreen/17-failure-card-d2-d6.png`.

**Root cause, read from source at `86d291f0`, with the runtime checked on disk:**

- `provider-supervisor.py:24` does `os.execvp(sys.argv[1], sys.argv[1:])` — a `PATH` search.
- `native.rs:1727` `resolve_claude_bin()` tries `$RICHOS_CLAUDE_BIN`, then `$HOME/.local/bin/claude`,
  then falls back to the bare name `"claude"`. Under the scratch home the second step misses, so it
  returned the bare name.
- `engine_profile.rs:191` then sets `.env("PATH", self.runtime.path())` on the child, and
  `runtime.rs:111` defines that as `format!("{}:/usr/bin:/bin:/usr/sbin:/sbin", root.join("bin"))`.
- **Positive control:** `claude` exists at `/Users/alex/.local/bin/claude` (a valid arm64 Mach-O) and
  the app process's own `PATH` does contain `/Users/alex/.local/bin` — but the child's does not.
  There is no `claude` in the engine runtime's `bin`, nor in `/usr/bin` or `/bin`. So the bare name
  cannot resolve, by construction.

**Why this is more than a QA artifact.** The three-step resolution order is documented in
`native.rs` as a deliberate design with step 3 as "the last resort". **Step 3 can never succeed in
the app**, because the `PATH` it would search is replaced before the spawn. On the CEO's real home,
step 2 hits and returns an absolute path, so he would never see this. A user who installed Claude
Code by Homebrew or npm — not at `~/.local/bin/claude` — would see it on first run, and would be
told to keep retrying. **That production-impact claim is a hypothesis from the code; I could not
reproduce it under another user's install, and the way to settle it is one launch with a `PATH` that
has `claude` somewhere other than `~/.local/bin`.**

### 1b. Second configuration — the CLI is not signed in

The orchestrator relaunched with `RICHOS_CLAUDE_BIN=/Users/alex/.local/bin/claude`. The boot log then
reads `compute connection: starts with the first cancellable request over /Users/alex/.local/bin/claude`,
and the provider starts. The turn still fails:

```
{"event":"TurnInterrupted","reason":"cognition protocol: \"Not logged in · Please run /login\""}
{"event":"TurnInterruptionCause","record":{"cause":"not-signed-in","ceoMessage":"I couldn't start
 that, because I'm not connected to your Anthropic account right now — either nobody has signed in on
 this Mac yet, or the sign-in ran out. You can connect it in Settings, under Account connection, and
 then send this to me again.","offersRetry":false}}
```

**This settles the brief's open question: the keychain symlink does not sign the CLI in.** The scratch
home has `Library/Keychains` symlinked to the real one, and the CLI still reports `Not logged in`.

**And this failure is handled well** — it names the cause, names where the fix lives, and correctly
offers **no** retry control, because retrying cannot help. Screenshot:
`22-check0-not-signed-in-card.png`.

## 3. Contrast — measured in both themes, nothing eyeballed

Method: from the live window captures, foreground taken as the text core and background as the modal
color of the crop; for light text over the animated nebula I also computed worst-case local
background, and for the fading temporary line I measured across 12 frames and took it at full
opacity. Every number below is computed, not judged.

**Dark mode — 38 nodes measured, lowest 4.96:1. All pass.**
Setup sheets 5.78–14.78:1 · chrome and sidebar 5.51–6.56:1 · onboarding card 6.09–13.02:1 ·
failure cards 5.51–12.06:1 · in-flight states 6.48–14.55:1 · voice bar 6.16–14.55:1 ·
settings 5.14–14.78:1 · splash 5.29–15.95:1 (worst-case local background 4.96–9.91:1) ·
D7 line at full opacity 7.68–10.14:1.

**Light mode — 24 nodes measured, lowest 4.72:1. All pass.**
Chrome and sidebar 4.99–5.83:1 · composer placeholder 5.37:1 · failure cards 5.37–18.07:1 ·
"Stopped after Ns" 6.70:1 · user bubble 5.50:1 · settings 5.37–18.07:1.
**The thinnest margin in the build:** the primary gold button ("Start the questions", "Set it up",
"Connect account") is dark text `rgb(12,19,34)` on `rgb(156,124,52)` = **4.72:1**, which clears 4.5:1
by 0.22. It passes; it has no room to drift. `34`.

**Non-text indicators (3:1 floor) — all pass.** Inactive theme icons 5.58–6.62:1; toggles 3.83–5.94:1;
active sun glyph on gold 3.83:1. The focus ring is a clear gold outline and is plainly visible (`35`).

**Declared exemption.** While a modal sheet is open the app dims the content behind it; those nodes
measure 1.77–1.85:1. I am calling that exempt because the content is inert and not meant to be read
while the sheet is up — and I am declaring it rather than quietly dropping it. **Positive control:**
the same nodes measure 5.51–6.56:1 the moment the sheet closes, which is how I know the low reading
is the dim and not the palette.

## 4. New defects, with repro

**#4 — home screen does not fit at 1024x700.** *Ran it on screen.* Resize the window to the app's
own documented minimum (it restored this size itself on the next launch) and open the home screen.
"INFRASTRUCTURE" loses its final E; the floating chip "Initiative · Product" is cut mid-word by the
"This is what your home screen could look like…" panel that sits over it; "Organization · Product"
lands on top of the PRODUCT label. Expected: at a supported size, no label is clipped and chips do
not collide. Control: all three are clean at 1400x880. `36`, `37`, `38`, `39`.

**#5 — the explanatory paragraph captions the wrong button.** *Ran it on screen.* On the company
sheet, *"Not now is fine. I'll leave the message box switched off until you pick one, and the button
to do it stays right there."* sits flush against the bottom edge of **Add this company**, with zero
gap, while the **Not now** button it describes is below it with normal spacing. Every other paragraph
on these sheets has clear spacing. Expected: the sentence sits with the control it explains. `31`.

**#6 — the dead composer looks alive.** *Ran it on screen.* Defer the company sheet, then click the
message box and type. The box reads **"Talk to Rich…"**, shows no disabled styling, and silently
discards every keystroke. The sheet did warn that the box would be "switched off", but the box itself
never says so. Expected: a switched-off input looks switched off and says why. Control: after adding
a company, typing in the same box works immediately. `07`, `08`.

**#7 — the send control has no accessible name.** *Read live from the accessibility tree.*
`AXButton` with `AXTitle = "▷"` and an empty `AXDescription`; the string "Send" exists only as
`AXHelp`, a tooltip. A screen-reader user hears a geometric shape. The talk control right beside it
is named correctly, which is the control. The composer itself is unnamed but does expose
`AXPlaceholderValue = "Talk to Rich…"`.

**#8 — "send this to me again" with nothing to send.** *Ran it on screen.* The not-signed-in card
tells the user to send the message again, but the composer is empty and this card — unlike the
`[Errno 2]` card — has no **Put it back in the box**. `22`.

**#9 — the temporary line wraps awkwardly.** *Ran it on screen.* "→ 1 new / memory" splits across
two lines, the second right-aligned. Legible, just untidy. `33`.
