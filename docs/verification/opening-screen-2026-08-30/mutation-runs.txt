THE OPENING SCREEN — THE THIRTEEN RUNS THAT PROVE THE SUITE CAN FAIL
====================================================================

`app/ui/tests/splash.js` reports 13/13 against the tree as it stands. That number is worth
nothing on its own: a check that has never failed has proven nothing, and this repository
has produced both kinds of green in one week — a scanner reporting CLEAN over an empty
corpus, and a `run.js` reporting "all 4 suites passed" over a suite it was not running.

So every check was run RED, once, by breaking the thing it guards in the SHIPPED source
(`app/ui/splash.js`, `app/ui/splash-library.js`, `app/ui/splash.css`, `app/ui/main.js`,
`app/crates/richos-core/src/config.rs`) and watching the suite say so.

The driver applied exactly one edit per run, REFUSED to proceed unless the target string
matched exactly once, restored the file from a copy taken before the edit whether the run
passed or failed, and `git status` was clean of stray modifications afterwards.


THREE OF THESE DESERVE A NOTE
-----------------------------

  * MUTATION 1 EXPOSED A REAL DEFECT IN THE SUITE, AND THE SUITE WAS FIXED RATHER THAN THE
    MUTATION ABANDONED. Making the library file contain a function — `"round": "8.1"` to
    `"round": String("8.1")`, valid JavaScript and invalid JSON — did not turn check 1 red
    on its first attempt. It turned the WHOLE SUITE into a crash before check 1 existed,
    because `libraryFromDisk()` parsed at module load and threw there. `run.js`'s evidence
    gate would have caught that correctly as a suite producing no evidence — but the check
    written to catch exactly this could never have been shown to go red, which is the
    defect this directory's whole gate exists to refuse. The parse now catches its own
    failure into `LIBRARY_ERROR` and check 1 asserts on it. Mutation 1 also reddens checks
    3, 5, 6 and 8, which is the right answer rather than noise: with no library there is
    nothing to draw, nothing to photograph and nothing to strike.

  * MUTATION 3 WAS A BAD MUTATION ON ITS FIRST RUN. Adding a misspelled token
    (`"surface_TYPO"`) alongside a correct `"surface"` left the entry perfectly valid, so
    check 3 stayed green — correctly. The mutation was corrected to RENAME the real token,
    which removes it, and the check went red naming the entry.

  * MUTATION 13 WAS A BAD MUTATION ON ITS FIRST RUN, and the reason is the interesting one.
    A 40ms busy-wait placed at the top of `start()` ran on BOTH arms of the measurement,
    including the one where the splash is switched off and returns immediately — so it
    delayed both launches equally and the DELTA did not move. That is the measurement
    working: it times the splash's own cost, not the machine's. Moved below the switch
    check, where only a launch that actually draws pays it, the same 40ms turns check 13
    red at once.
