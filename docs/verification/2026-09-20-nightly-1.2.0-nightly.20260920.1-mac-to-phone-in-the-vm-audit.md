# Mac → phone on nightly `.20260920.1`, measured in the test VM with real model turns

**The half nobody had measured is now measured, and it is fast. The half everybody assumed was
fine is the slow one.**

`.7` and `.8` both ended on the same sentence: *Mac → phone was NOT REACHED, because the guest has
no Claude login.* The guest is logged in now — it took about four minutes, not next month — and six
real model turns ran on the CEO's subscription inside the VM.

| | |
|---|---|
| **Rich's reply, Mac window → phone page** | **Under a second on all five turns.** On the best-resolved turn the two screens are simultaneous to within 0.17 s. Widest upper bound across the five: **1.25 s** |
| **The message the CEO types on the Mac → phone page** | **1.3 s to 6.1 s on four of the five turns.** This is the slow leg, and it is the one nobody was looking at |
| **Phone → Mac, on this build** | **689.3 ms** to the Mac's own ledger, bubble on screen in (546.6, 708.9] ms. `.8` measured 181–635 ms on a quieter host |
| **First reply after send, on the Mac (§55)** | **43–504 ms** — fast. But it is never the words *"On it!"*: **zero** occurrences across **210** distinct rendered states in six live turns. What appears instead is *"Working" / "Rich is working" / "Nothing has come back yet"*, held for 10–15 seconds |

**The verdict in one line:** the round trip is closed and both directions are usable. Two things
should be looked at before this is called finished — the 1–6 second lag before your own typed
message shows up on the phone (defect 1), and *"Nothing has come back yet"* sitting on the Mac's
screen for ten seconds while Rich is in fact working (defect 2).

## Verification mode

macOS 15 guest in the Tart test VM (`--vm ray9`), app window **1024×700** at `(10,60)`, Safari in
the same guest standing in for the phone at `(1044,60)` **620×700** — **side by side, 10 px of
clear space, never overlapping**. One app window. Two-user test: **yes** — the Mac and the phone
page are the two ends and the same thread (`Running`) was open on both throughout.

**Nothing was rendered, installed or launched on the host.** The host's `pgrep -fl richos-tauri` was
empty before the run and is empty after it. No `pmset`, no lock, no sleep, no modifier keystroke,
no display change. `caffeinate -is` only, inside `run.sh`. The host's own login keychain was never
written to.

**A deviation from the brief, stated because it changes nothing but the reader deserves to know.**
The brief says *"pair a phone page the way the `.8` audit did (headless WebKit on the host through
the tailnet)"*. The `.8` audit did not do that — it used **Safari inside the guest**, side by side
with the app. I followed what `.8` actually did, for a reason the measurement depends on: the
quantity asked for is the gap between a repaint in the Mac's window and a repaint on the phone's
page, and a headless browser on the host has no repaint to observe and is on a different clock. A
browser in the guest satisfies the *"no browser window on the host"* constraint more strictly than
a headless host process would, not less.

Every claim below is **verified live on the guest's screen** unless it says otherwise. Contrast
ratios are computed from rendered pixels, never eyeballed.

## Getting the guest signed in — four minutes, and it did not touch the host's login

This is the step `.7` and `.8` both stopped at, so it is written out in full.

**1. The guest had no `claude` binary at all.** `provision-guest.sh` never installs one —
`grep -i claude provision-guest.sh` returns nothing. `run.sh:256-257` exports
`RICHOS_CLAUDE_BIN=/Users/admin/.local/bin/claude`, which is a path to a file that does not exist
until somebody puts one there. The host's binary is a Mach-O arm64 executable and the guest is
arm64, so it copies straight across:

```
$ scp .../claude/versions/2.1.277  admin@<guest>:/tmp/claude-bin
$ ssh admin@<guest> 'mkdir -p ~/.local/bin && mv /tmp/claude-bin ~/.local/bin/claude && chmod +x ...'
2.1.277 (Claude Code)
```

**2. The credential went in as a FILE, not a keychain item, and that turned out to be both safer
and the only thing that works.** The brief's route was `security add-generic-password … -w` inside
the guest with the value on stdin. **It does not work, and it fails silently in the worst possible
way** — proved with a dummy value before the real one went anywhere near it:

```
# probe 2: `-w "$KC"` — security swallows the KEYCHAIN PATH as the password
add-exit=0  find-exit=0 len=65      # 65 = the length of the keychain path
RESULT: STDIN PATH DID NOT WORK

# probe 3: `-w` last, keychain made default first, value piped on stdin
add-exit=0  find-exit=0 len=0       # item created with an EMPTY password
RESULT: STDIN PATH DID NOT WORK
```

`security` does not read the password from stdin when there is no tty; it creates the item with an
empty password and **exits 0**. A walk that had trusted the exit code would have gone on to report
a login failure as a product defect.

Claude Code's own binary names both stores (`strings` finds `Claude Code-credentials`,
`security find-generic-password`, **and** `.credentials.json`), so the credential was written to
`$CLAUDE_CONFIG_DIR/.credentials.json` — mode `600`, inside the fixture home, transported by `scp`
of a `umask 077` file that was deleted from the host the moment it landed. **The value was never
printed, never echoed, never on any command line, never in any log, and is in no frame.**

Its shape was inspected without revealing it — `{"claudeAiOauth": {accessToken(108),
refreshToken(108), expiresAt, refreshTokenExpiresAt, scopes[6], subscriptionType, rateLimitTier}}`.
`expiresAt` sat about six hours in the future, so **no token refresh could occur during the walk** —
which is why the rotation risk the brief flagged never happened.

**3. Login confirmed with no model turn**, under exactly the environment the app hands `claude`:

```
$ HOME=<fixture home> CLAUDE_CONFIG_DIR=<fixture home>/.claude  claude auth status
{ "loggedIn": true, "authMethod": "claude.ai", ..., "subscriptionType": "max" }
```

**And the app said so itself, on screen** (`02-account-connected.png`): *"Your Anthropic account is
connected."*

**4. The host was NOT logged out.** Asked after the run, before writing a word of this:

```
$ claude auth status      # on the HOST
{ "loggedIn": true, ... }
```

**The CEO does not need to run `/login`.** Writing the guest's credential to a file in the guest's
own disposable home, rather than into a keychain, is why: nothing in the guest ever wrote to the
host's keychain item.

## Two harness defects had to be fixed before a single number could be taken

### H1 — `run.sh --engine` has never worked. The app reported the engine missing.

`run.sh` untars the engine payload with

```
mkdir -p '$PAYLOAD/engine' && tar -C '$PAYLOAD/engine' -xzf '$PAYLOAD/engine.tar.gz'
```

and the release tarball's single top-level member is `engine/`:

```
$ tar -tzf richos-engine-1.2.0.tar.gz | awk -F/ '{print $1}' | sort -u
engine
```

There is no `--strip-components 1`, so `$RICHOS_ENGINE_DIR` ends up pointing at a directory whose
only child is `engine/`. `setup.rs::engine_looks_valid` wants `scripts/hooks/` and `VERSION` at the
top, finds neither, and the app opens on *"There's one thing I need on this Mac — the RichOS
engine"* (`00-launch-engine-missing.png`). Confirmed in the guest:

```
$ ls /Users/admin/testvm/ray9/engine
engine
$ ls /Users/admin/testvm/ray9/engine/VERSION
ls: ... No such file or directory
```

**Fix is one flag** (`tar --strip-components 1`). I lifted the directory by hand and relaunched;
the app then logged *"engine directory: … (via RICHOS_ENGINE_DIR, engine 1.2.0 … taken as named)"*
and **`first-run setup: nothing missing.`**

**This is why `.7` and `.8` saw no engine.** It was read as "the guest has no engine because nobody
gave it one". A guest WAS given one, twice over, by a flag that silently puts it one level too deep.

### H2 — the prepared keychain still costs a password prompt, and the prompt is invisible to the harness

`.8` defect 5 asked for *"a real, unlocked, empty login keychain"* in the fixture. `keychain.sh`
now ships it and `run.sh` calls it — real progress, and the `Keychain Not Found` dialog is gone.

But pressing `Set my phone up` still raises **`security wants to use the "login" keychain.`** with a
password field (`08-code-screen.png`), behind the sheet, over *"Getting this Mac ready…"*. Worse:

```
$ wins.sh                      # every visible process window in the guest
richos-tauri :: RichOS
```

**The modal does not appear in the window list at all.** A tester who does not already know to look
for it sees the app hang. It is reachable by clicking its coordinates — `System Events` then names
it back as `text field Password: of window 1 of application process SecurityAgent` — but nothing in
the harness's own inventory says it is there. The keychain needs the app's `security` call on its
ACL, or `keychain.sh` needs to add a `-A` style grant at creation.

## Step 3 — Mac → phone, five turns

`T_SEND` is the guest's clock at the press; both panes are captured **inside the guest, in one
process, on one clock**, by two concurrent threads. The deciding frame in each pane was chosen by
**OCR, not by a hash change**: it is the first frame of that pane in which the agreed token appears
**twice** — once in the message I typed, once in Rich's reply carrying it back. A hash change alone
cannot tell my own bubble from the reply.

### Rich's reply, Mac window → phone page

| # | message | reply on the MAC | reply on the PHONE | **MAC → PHONE lies in** |
|---|---|---|---|---|
| m1 | `reply with exactly: ray nine one` | +10,820.3 ms | +11,270.8 ms | **(−8, +577) ms** |
| m2 | `reply with exactly: ray nine two` | +10,497.2 ms | +10,506.1 ms | **(−1,234, +1,250) ms** |
| m3 | `reply with exactly: ray nine three` | +12,735.1 ms | +13,553.2 ms | **(−6, +1,086) ms** |
| m4 | `reply with exactly: ray nine four` | +14,525.4 ms | +14,517.9 ms | **(−167, +149) ms** |
| m5 | `reply with exactly: ray nine five` | +12,959.9 ms | +13,834.7 ms | **(−11, +1,067) ms** |

Point estimates, for the record: **−7.5, 8.9, 450.5, 818.1, 874.8 ms** — min −7.5, median 450.5,
max 874.8.

**Why an interval and not a number with a `±`.** A pane's state appeared somewhere after that
pane's PREVIOUS frame, so the gap lies in `(tB[b−1] − tA[a], tB[b] − tA[a−1])`. Quoting the
midpoint invites the midpoint to be read as the measurement. The host was carrying other agents'
work throughout — load average **12–27** — and the capture loop stalled accordingly: the median
inter-frame gap per pane ran **77 ms (m1), 83 ms (m2), 189 ms (m3), 131 ms (m4), 98 ms (m5)**, and
in m5 the loop stalled for 3.5 s immediately after the press. `.8`'s 45 ms loop was a one-pane
capture on a quiet host; two panes on a busy one costs what it costs, and the honest response is to
widen the interval rather than quote a false precision.

**What the five intervals jointly support:** every one is contained in (−1.25 s, +1.25 s), and
**four of five are contained in (−0.17 s, +1.09 s)**. The tightest-resolved turn, m4, puts the two
screens within **167 ms of each other in either direction**. So: *Rich's reply reaches the phone
within about a second of appearing on the Mac, and probably much closer than that.* The instrument
cannot resolve finer on this host, and saying so is the finding, not a gap in it.

**A negative number is not an error.** The Mac **streams** the reply token by token while the phone
receives the finished message in one piece, so the phone can legitimately render the complete text
in the same instant the Mac's pane is still painting it. m4 is that case.

## Step 6 — the heavy-window rule, and why the rule as written did not do its job

The brief's gate is `pgrep -f 'nightly-local.py|run.js'`. I ran it before the boot and before every
single sample. **It was EMPTY every time** — eight checks, at 05:48, 05:48, 06:12, 06:16, 06:19,
06:22, 06:25 and 06:30Z. **I waited zero minutes.**

**And the host was loaded anyway.** At 06:22Z, with the gate reading empty:

```
$ uptime
load averages: 27.33 19.28 16.56
$ ps -Ao %cpu,comm -r | head
 98.5 systemstatusd
 94.4 fseventsd
 74.4 com.apple.Virtualization.VirtualMachine
 55.2 webstorm
 16.4 com.apple.WebKit.WebContent.Development   <- playwright-browsers/webkit-2311
```

A Playwright WebKit and WebStorm are not `nightly-local.py` and are not `run.js`. The gate named two
process names; what actually costs a timing run is **CPU**, and nothing in the brief measured CPU.
That is why m3's sampling was 2.5× coarser than m1's and why m5's loop stalled for 3.5 seconds. It
did not invalidate anything — the intervals above already carry the cost — but a gate that reads
empty on a load average of 27 is a gate that will eventually certify a run it should have held.
**Recommend: gate on `uptime`'s 1-minute load as well as on process names.**

## Defects, ranked

### 1. HIGH — your own typed message takes 1–6 seconds to reach the phone, while Rich's answer to it arrives instantly

Measured above: **(1.60, 1.99) s, (1.32, 1.91) s, (1.79, 2.06) s** on the three tightest-resolved
turns, and **(5.62, 6.09) s** on m5. Meanwhile Rich's reply to those same messages crossed in under
a second every time.

**Why it matters to the person, not the profiler.** Picture him at the desk with the phone beside
the keyboard, which is exactly the two-screen situation this feature creates. He types, presses
send, and the Mac shows it immediately — and the phone sits there showing the *previous* message for
up to six seconds. Nothing says "sending". Nothing says "sent". The phone simply looks stale, and
the natural reading of a stale screen is that the phone has dropped off.

Ordering is never wrong and nothing is ever lost — the echo always precedes the reply. It is
latency and its presentation, not correctness.

**What would settle the cause:** whether the phone page renders a Mac-originated message from the
live stream (as it plainly does for Rich's replies, which are fast) or waits for a poll/ledger read.
The asymmetry — same channel, same thread, same second, one direction fast and the other slow —
points at two different code paths for the two senders.

### 2. MEDIUM — *"Nothing has come back yet"* on screen for ten to fifteen seconds while Rich is working

`leg-m1-mac-nothing-has-come-back-yet.png` is the measured frame. The block reads:

```
Working for 4s  •
   ● Rich is working                                    3s
     Nothing has come back yet
```

and it holds, with the counter ticking, for the whole turn — **10.8 s (m1), 10.5 s (m2), 12.7 s
(m3), 14.5 s (m4), 13.0 s (m5)** — until the reply lands.

Two sentences are competing and one of them is discouraging. *"Rich is working"* with a live timer
is the reassuring half. *"Nothing has come back yet"* is a report of absence, and it is the last
line, which is where the eye settles. After ten seconds of reading that a reasonable person
concludes something is stuck. The words are doing the opposite of what the counter beside them is
doing, and §55's *"On it!"* — the sentence the CEO actually asked for — is nowhere on this path
(step 4). **Proposal, not a decision:** lead with the acknowledgement and drop the absence report.

### 3. MEDIUM (harness) — `run.sh --engine` silently installs the engine one directory too deep

H1 above. One missing `--strip-components 1`. Costs every future walk a relaunch, and has already
been read twice as "the guest has no engine".

### 4. MEDIUM (harness) — the keychain prompt is invisible to the harness's own window inventory

H2 above. The prepared keychain is real progress on `.8` defect 5; what remains is the ACL grant
and the fact that `wins.sh` cannot see the `SecurityAgent` modal that blocks the sheet.

### 5. LOW — `security add-generic-password -w` exits 0 after storing nothing

Not a RichOS defect — a macOS trap that will catch the next person who automates a credential into
a guest. Two spellings both fail silently (path swallowed as the password; empty password stored),
both with `exit 0`. Written up in full above so nobody re-derives it.

### 6. LOW — carried from `.8`, still true

* **The theme selector is checkboxes, not radios.** It is now **two** (`AXCheckBox|Light theme`,
  `AXCheckBox|Dark theme`) where `.8` found three — *"Follow the system"* is gone. Two mutually
  exclusive options are still radios, not checkboxes.
* **`Paired with Phone` is a near-empty sentence.** Settings still reads
  `AXMenuItem|Use Rich from your phone Paired with Phone` when the device reports a generic name.

### Fixed since `.8`

* **Defect 3 (tailnet join races `tailscaled`) — FIXED.** `run.sh` now waits for the daemon:
  *"the guest's tailscaled answered after 2 read(s) — state NeedsLogin"*, then joined cleanly.
  No `tailnet=not-joined`.
* **Defect 4 (join warns pairing will fail seconds before the certificate arrives) — FIXED.**
  *"certificate in hand and cached for the next run"*, no spurious warning.
* **Defect 5 (fixture has no usable keychain) — MOSTLY FIXED.** See H2 for the remainder.
* **Three stacked "Not now" offers at launch — FIXED.** One offer at launch, naming one missing
  piece; after the engine was wired, none.

## The instrument

Timing a press against a repaint across `ssh` is a way of measuring `ssh`. So the press and **both**
capture loops run inside the guest, from one Python process, on one clock — `measure2.py` starts two
`screencapture` threads (one per pane), sleeps 1.5 s for a baseline, issues the click itself, and
writes every frame's timestamp beside the press instant. `intake.jsonl`'s `at` is on that same
clock, which is what makes the phone → Mac leg exact rather than sampled.

`.8`'s instrument captured one pane. Mac → phone needs two, because the quantity is the gap between
two screens.

**Repaint detection is byte-identity of the captured PNGs.** Each region holds only a thread pane —
no clock, no pointer, no animation — so two frames of the same screen compress identically and a
hash change is a repaint. Regions: Mac `315,140,710,545`, phone `1058,290,600,400`; both were
captured once and inspected before any measurement (`raw/region-mac.png`, `raw/region-phone.png`).

**And the discipline `.8` paid for is still in force.** Focus is set through the accessibility API,
never by clicking — a synthetic click at a text field's coordinates lands ON the field but leaves
focus on the `AXWebArea`, so keystrokes go nowhere. Every send asserts the composer's contents match
the message **before a single frame is captured** and aborts if they do not. That assertion fired
zero times in this walk, which is the point: `.8` learned it as a false *positive*, a clean
measurement of a send that never happened.

**Then OCR on top of the hashes, which is new here.** A hash change cannot tell my own bubble from
Rich's reply — both are repaints in the same pane. The token count can: the agreed phrase appears
**once** as soon as my message renders and **twice** once the reply carrying it renders. Every
deciding frame in this audit was chosen that way and its OCR text is in the record.

## What would change the verdict

Three things, in order of what they would cost:

1. **The 1–6 second echo of your own typed message to the phone** (defect 1). It is the one number
   in this walk that is clearly outside what a person would accept, and it is on the leg nobody had
   been measuring.
2. **The words on the Mac while Rich works** (defect 2, and §55 in step 4). *"Nothing has come back
   yet"*, held for ten to fifteen seconds, is the wrong last line.
3. **A quieter host, or a load-aware gate** (step 6). The reply leg is under a second and almost
   certainly much tighter than that; a run on an idle machine would say how much tighter, and would
   also let the light-mode contrast of the in-turn status block be measured.

Everything else in this walk is settled. The engine, the login, the pairing, the round trip, and
the redaction all hold.
