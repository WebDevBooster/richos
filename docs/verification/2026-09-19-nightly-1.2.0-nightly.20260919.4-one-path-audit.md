## B1 — BLOCKER: a stale engine directory leaves the app unable to answer, with no offer and a misleading reason

This is the row the brief asked me to record exactly as found.

**What the user gets.** Launch 1's boot log said the engine was not usable. Nothing appeared on
screen. I went in through the door and typed the job. The turn produced **no answer at all**. On
screen, under a red `Stopped` rule:

> I lost my connection to the part of me that thinks, partway through. That kind of thing usually
> clears on its own, so asking again is worth a try.
> Your message is saved. I hadn't written any of my answer yet.
> `[Put it back in the box]`

**What actually happened,** from `app.log`:

```
[richos] turn interrupted [transient]: cognition io: .../Application Support/RichOS/engine: the engine
         there carries the right version and different contents — installed from 3313945b26b7, and this
         build pins adece4c069e4
[richos] text turn refused before it started (the spine refused the prompt)
```

**Three separate faults, and the third is the one that traps the user.**

1. **No offer.** The boot log says `first-run setup: this build installs engine 1.2.0.`, yet no setup
   sheet ever opened. The Settings menu has no Setup or Engine row either (frame 05), so there is
   **no user-reachable path to the fix**. On the fresh path the same build *does* offer it on entry
   (frame 14), which scopes the defect precisely: **engine absent -> offered; engine present with
   wrong contents -> silently not offered.**
2. **The reason is wrong.** Nothing was lost "partway through" — the turn was `refused before it
   started`. The sentence describes a mid-flight drop that did not occur.
3. **"Transient" is false, and it invites an endless loop.** The log labels a permanent identity
   mismatch `[transient]` and the card tells the user it "usually clears on its own, so asking again
   is worth a try". I took that advice: `[Put it back in the box]` restored the message correctly,
   I sent it again, and it failed identically — two identical error cards stacked, same two log
   lines. It will never clear on its own.

**User impact.** A user in this state has a RichOS that cannot answer a single message, is told to
wait and retry, and has no control anywhere in the product that would fix it.

Raised as `esc-20260919T152225Z-2e44d112`.

## The priming number, and why 10.8 s is not what it looks like

The brief predicted the first message after a refresh must not pay the ~11 s prime, and asked for
the number. **The number is 10,844 ms to first words**, which looks exactly like the prime it was
supposed to remove. It is not, and here is the evidence.

- `app-relaunch.log` after the install: `the front desk is ready before he types: 6771 ms, including
  the lease's own start — that is what his first message used to wait through (CEO §55)` and
  `a front desk is primed and waiting for the next new thread in qa-test-co: 5473 ms`. The prime was
  paid **before** typing.
- **The isolation test.** A second, deliberately minimal message ("reply with exactly: ok") in the
  same already-warm thread took **15,052 ms** to first words — *longer* than the first. If 10.8 s
  were prime overhead, the second message would have been dramatically faster. It was slower.

So sixsec1's fix holds: the first message is not charged the prime.

**What the numbers are, plainly:**

| | measured |
|---|---|
| send -> visible acknowledgment ("Rich is working / Nothing has come back yet") | **151 ms** |
| send -> first words, first message after install ("On it!") | **10,844 ms** |
| send -> first words, second message in the warm thread ("ok") | **15,052 ms** |

Both first-words figures sit above the 9 s the CEO called fine in §55. The 151 ms acknowledgment may
be what that ruling actually addresses. That reading is his, not QA's — recorded here as measured.

## New defects, ranked

**D1 (medium) — the primary button on the phone sheet moves under the cursor, and presses are lost.**
`Set my phone up` took **three** presses. Each of the first two re-polled the phone's Tailscale
state, re-rendered the status line between its one-line and two-line variants, and moved the button
±23 px; both presses were swallowed. I ruled out a timer: with no clicks the button sat still for
21 s across 12 captures, so the re-render is **press-triggered**. This is the audit-9 row 4 shape
(*"the sheet re-rendered under my cursor... my click aimed at Close landed on nothing"*) in a second
place. The fix pattern already exists in `main.js` — resolve the state first, paint once.

**D2 (low) — the Settings menu gives no sign that a pairing code is live.** With a code counting
down, the `Use Rich from your phone` row looks identical to its idle state. Minor, but the code
expires in five minutes and the row is the only way back to it.

**D3 (low, and it counts in the user's favor) — the phone-state sentence is accurate and actionable.**
Not a defect; recorded because it is the thing D1 rides on. When his phone's Tailscale dropped, the
sheet changed itself to "Your phone (HONOR X6b) is on this network but Tailscale is switched off on
it. Turn it on in the Tailscale app." That is correct, specific and tells the user what to do.

**Carried, seen and recorded as the brief asked:** the gear-vs-menu split (the splash's Settings has
no Theme row, the desk's does — consistent with §15's always-dark start screen); one Settings sheet

are void and are not counted anywhere above.

space 0.69 s after it returned. The first attempt failed for a reason worth recording: `pgrep -f
richos-tauri` also matches a concurrent `cargo build --bin richos-tauri` in another worktree, so the
trap fired on the wrong process. Keying on the window instead is what worked.

## Privacy

Every committed frame is a **window crop**, so no browser, no desktop and no file names are in any of
them. His address appears on four of the phone-sheet screens and is black-boxed in all of them.

**OCR gate: 0 hits over 19 frames.** The gate runs a **positive control first** — the same reader, on
the un-redacted source, must find the address, and it does (1 hit). Without that control a gate that
simply cannot read the image would report zero for the wrong reason.

**The gate was not sufficient on its own, and that is worth recording.** Frame 08 carried a
vertically **clipped** address at the sheet's top edge — half-height glyphs that tesseract cannot
read and therefore cannot flag. The gate passed it. I found it by looking at the frame, and blacked
that line out by hand. Every frame containing the sheet was then checked by eye as well as by the
gate. A reader-based gate is blind to text it cannot read, so it can only ever be the second check,
never the only one.

**His phone was never touched** beyond read-only `adb` state queries: no pull, no install, no
uninstall, no settings change, no Tailscale change, and Chrome was never opened, so no phone frame
and no account surface exists in this record.
