## B1 — The blocker: this nightly's interface was not walked, and could not be

**Basis: ran it, plus source at `ecf8cdaf`.**

The app decides its own presentation from three facts, all of which must hold for a normal launch
(`richos/app/src-tauri/src/activation.rs`; documented at `richos/app/README.md` §"Booting the app in
a test"): **B** the executable sits in a `.app` with this build's identifier; **D** it writes to
`$HOME/Library/Application Support/<identifier>`; **P** `getppid()` is 1.

A QA harness must hold the process it boots, so **P is false by construction** — always, for any
harness anyone will ever write. That is deliberate and it is a good design: it is what keeps a test
boot off his monitor. Its consequence is the blocker. The window is then built **invisible**, not
merely unfocused:

    richos/app/src-tauri/src/main.rs:1205
        .visible(activation.presentation == activation::Presentation::Regular);

Both of my boots confirmed it, first line of stderr:

    [richos] activation: accessory — no Dock icon, no window on screen, no focus taken, because this
    is not an installed launch: a program is holding this process (parent pid 37495) …

An invisible window has no window-server surface, so `screencapture` has nothing to capture and the
accessibility API has nothing to address. The README's two stated ways out are `window.show()` (not
callable from outside the process) and `RICHOS_ACTIVATION=regular` (**forbidden by this brief, and
correctly so — it takes his keyboard**).

**The repo's own answer confirms there is no third way.** The only harness here that drives the real
Tauri IPC, `richos/app/scripts/native-responsiveness.test.py`, does not drive the shipped app at all:
it copies the source tree, rewrites `main.rs`, changes the bundle identifier to
`com.richos.native-regression` and builds an instrumented binary. That is forbidden here ("do not
build the app") and it would not be the published bundle even if it were allowed.

**So these were not performed, and are reported as not performed rather than inferred:**

- the first screen, and what it says about the speech model (item 1's UI half)
- the real model download, its progress UI, and its refusal path (item 2)
- the silent voice turn (item 3)
- the text turn and thread-after-restart (item 4)
- the updater's on-screen answer (item 5's UI half)

**What would make them testable** — in ascending order of effort, for whoever decides:

1. A fourth activation value, e.g. `RICHOS_ACTIVATION=offscreen`: accessory policy (no Dock icon, no
   focus, nothing on his monitor) but the window **visible** to the window server, so
   `screencapture -l<id>` works and the existing three-fact rule is untouched. Smallest change; keeps
   his screen safe by the same argument the current design uses.
2. A `RICHOS_DEVTOOLS=1` opt-in exposing the webview over CDP, so a QA pass can drive the real
   shipped renderer the way it drives any other web surface.
3. Accept that nightly QA runs on a second Mac or a VM where taking the screen costs nobody anything.

Until one exists, every nightly will arrive in the same state this one did: verified up to the boot
line, unlooked-at above it.

## Defects

### D1 — Two sign-in strings are not American English (Low, user-facing)

**Basis: found in the shipped binary's strings, confirmed in source at the nightly commit.**

    ecf8cdaf:richos/app/crates/richos-core/src/provider_auth.rs:21
      AuthState::Cancelled => "Sign-in was `cancelled`. You can try again when you are ready.",

    richos/app/ui/main.js:4140
      "Sign-in could not be `cancelled`. Try again."

American English is the standing rule for every string a person reads, and the audience is US-based.
The American spelling is `canceled`. Both of these sit on the **first-run account-connection path** —
the first thing he does on a fresh install — so they are not buried.

Scoped, so the fix is not over-applied: the other matches in the same sweep are **not** defects and
should be left alone — `native.rs:167/173/341` use the word as an ACP **protocol wire value**
(third-party vocabulary, exempt); `steering.rs:933/944` are test names; `native.rs:2540` is a comment;
and the vendored Tauri updater's own strings are third-party. The dialect rule does not bind code
identifiers or external protocol values.

### D2 — The readiness log still tells him to go find whoever set RichOS up (Low, operator-facing)

**Basis: ran it (the line is in both boot logs), plus source at the nightly commit.**

Boot prints, for `model-missing`:

> My ears aren't installed on this machine yet — whoever set RichOS up adds those.

The code's own doc-comment on `SpeechReadiness` (`richos-voice/src/stt.rs:487-496`) says precisely why
that is now wrong:

> `SttError::ceo_message` deliberately gives `BinaryNotFound` and `ModelNotFound` the SAME words …
> because to the CEO they were the same event: somebody else had to fix it either way. **Once RichOS
> can fetch its own model that stops being true** …

This build can fetch its own model, so the sentence is stale for the `ModelMissing` branch —
`stt.rs:551` still routes `ModelMissing` through `ModelNotFound`'s message, and
`main.rs::voice_readiness` puts it in the payload as `reason`.

**It is Low, not Medium, and the reason is the part that matters:** the UI **never reads `reason`**
(`ui/main.js:3124-3131`), so he does not see this sentence — he sees the offer. The harm is confined
to the boot log and the command's payload, where it tells an operator the opposite of what the app
will do, in the one log `gui-boot.test.sh` exists to hold every line of to account. It is worth a
one-line fix; it is not worth blocking on. **I did not verify what is on his screen and this entry
does not claim to.**
