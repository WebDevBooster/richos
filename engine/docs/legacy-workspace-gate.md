# Legacy maintenance gate

`scripts/lib/legacy-workspace-gate.py` is a root-only macOS gate library. Its packaged administrator entry point exposes separately approved capture, recovery, retirement and job operations. It has no service activation or reboot command. Do not invoke it on repositories with active work. Normal worker requests cannot authorize a gate.

`LegacyGate(vault, inspection_context=...)` requires an existing dedicated root-owned mode-0700 vault with protected ancestors. Only that configured vault is used; cross-device roots or descendants refuse. `stage(report, approved_sha256=...)` requires explicit offline authorization for the exact planner report. It regenerates the plan as the explicitly approved unprivileged repository owner before changing anything. The report binds that account UID, primary GID and home together with explicit absolute transaction-directory and ledger-file paths. Root never uses its own HOME or runs repository Git commands to build this inventory. A fixed packaged helper runs with the approved UID/GID, no supplementary groups, a clean environment and stdin JSON. Git uses its fixed system executable with global/system configuration, hooks and filesystem monitors disabled. Changed owner or history context cannot resume another gate. Changed evidence, incomplete inventory, live/unknown owners, cross-repository overlaps or other planner blockers refuse. Same-repository nested native worktrees remain distinct targets in the plan but move with their consolidated ancestor root.

The approved plan explicitly lists temporary parent gates and their sibling entries. Offline approval covers the brief access interruption to those siblings, including unrelated repositories. A changed parent namespace requires a new review. Before changing source parents, the gate durably records their ownership, modes and inode identity. It protects each parent, opens and verifies that exact directory and renames source roots relative to the held directory descriptor. The destination is private recovery storage on the same filesystem. The two worktree/Git namespace moves are individually journaled, never represented as one atomic transaction. A parent can still be renamed through a user-owned ancestor; failure to reopen its pinned identity leaves an explicit admin recovery case rather than modifying a replacement path.

Before changing source metadata, new gates write and fsync one complete original metadata snapshot. Every alias therefore retains its original owner and mode even when an earlier alias has already changed the shared inode. Historical partial journals remain readable. Protection proceeds from directories to their children, changing ownership and permissions on regular files as well as directories. It preserves interior symlink text without following targets. A full-tree preflight rejects existing unsupported objects before any mutation.

Regular-file hardlinks are supported only when every alias is inside the approved gate set and one physical and logical maintenance target. Cross-target groups, outside aliases and multiply linked symlinks refuse. The live link count must equal the number of observed aliases after protection and again before frozen access. Completed retirement checks the remaining aliases against their current link count, so interruption between two unlinks is replayable. A link that appears outside the set during staging leaves a recoverable partial gate and cannot authorize deletion.

The exact Darwin `UF_TRACKED` and `UF_HIDDEN` flags are recorded and preserved on the original inode. Other flags, filesystem boundaries, special nodes, setuid/setgid modes and extended ACLs refuse. Native `acl_get_link_np` checks the object itself without following symlinks or spawning one process per file. Missing paths, changed inode stamps and unreadable ACL metadata refuse. ACL-bearing objects are not treated as ordinary mode-only files.

Open file descriptors and mappings can still write while the current boot continues. Old directory descriptors cannot bypass the protected inode's directory permissions. Only after complete inventory verification is a `gated_boot_id` written. A crash before that receipt may require an additional reboot. Missing, malformed or unchanged boot identity cannot establish a cutoff. The source parents regain their known metadata after protection finishes. The originals remain in the vault; new paths created at their old names are separate work.

`resume(id)` retries incomplete staging against recorded identities. Truncated journals, replaced parents or roots and unexpected metadata changes fail closed. No automatic rollback is attempted. `inspect(id)` distinguishes staging, gated, restoring and restored states. `frozen_view(id, approved_sha256=...)` holds the gate lock, verifies the approved plan, all protected inodes and a positively different boot, then yields the original-to-vault root mapping for the privileged capture and retirement executors. Leaving that context releases the lock. It grants no deletion authority.

`restore(id, approved_sha256=...)` is a separate explicit admin decision available only after a verified later boot. Failed partial staging may also be restored after a different valid starting boot: only journaled metadata is restored and exact unmoved roots are preserved. Partial restoration never establishes capture readiness. Late hardlinks are preserved during this recovery rather than deleted. It restores metadata inside the vault, returns ownership last and renames roots back through protected, pinned parents. It never overwrites an existing original path. Interrupted restoration is journaled and cannot be mistaken for a frozen capture view. Neither completed restoration nor retained recovery storage counts as reclaimed disk space.

`require_root=False` exists only for disposable workflow tests. Those tests use real Git repositories and same-filesystem renames, preserve staged/working/untracked/symlink bytes, demonstrate late open-descriptor writes and exercise interrupted operations. They simulate a different boot and do not prove privileged revocation, file-ID exclusion or an installed reboot workflow. Actual root boundary acceptance remains required before any deployment. No live repository gate has been performed.

The separate capture, mutation and retirement executors now verify post-boot archives, preserve Git recovery refs, remove exact selected worktree registrations and coordinate branch deletion. An immutable armed job runs these operations through the broker maintenance worker. A parent target cannot be retired while a contained registered target must remain. Retirement receipts bind the approved target, its held inode and verified archive before omitting it from restoration. Interrupted deletion is replayed before the gate can reopen. Unique or unclassified legacy archives have no automatic expiry. Actual installed gate and reboot acceptance remain outstanding; see [retirement](legacy-workspace-retirement.md) and [automatic jobs](legacy-workspace-job.md).

The protected release includes `legacy-workspace-admin.py`. Invoke it only with `/Library/Developer/CommandLineTools/usr/bin/python3 -I -S -B` and its absolute installed path. The admin entry point validates the protected release manifest, interpreter/import paths and installed owner/repository policy before importing the gate. `plan` requires explicit `--owner-uid`, `--transactions`, `--ledger` and one or more `--repository` aliases. It emits a review artifact and creates no gate. `stage` additionally requires `--report` and `--approved-sha256`; the exact report must regenerate under the owner and installed repository policy before even the dedicated `legacy-gates` vault is created. `inspect`, `resume` and `restore` require the existing `--gate-id` and matching inspection context; restoration also requires the explicit approved hash. These commands are administrator operations outside the worker socket protocol. Packaging the commands does not approve offline maintenance.

The owner-inspection tests use small disposable repositories to verify history isolation, dropped-identity subprocess arguments, failed-child refusal and authorization checks before vault writes. They do not perform a root legacy gate or establish its still-pending installed reboot acceptance.
